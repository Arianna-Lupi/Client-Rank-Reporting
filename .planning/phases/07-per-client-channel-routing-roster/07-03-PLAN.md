<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| external caller -> cron endpoint | Untrusted HTTP request; only a valid `Bearer CRON_SECRET` may trigger the run |
| Redis map -> posting path | channel ids come from the map; an absent mapping must skip, never fall back to a wrong channel |
| handler -> Slack chat.postMessage | Proactive posts use the bot token; only the mapped channel id and rendered blocks are sent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-08 | Spoofing | cron endpoint auth | mitigate | `isAuthorizedCron` gate returns 401 before any config/work; blank secret never authorizes |
| T-07-09 | Information disclosure | per-client error/post logs | mitigate | Logs are siteUrl-only; never interpolate report.message, the bot token, or the cron secret (ASVS V7) |
| T-07-10 | Tampering | wrong-channel delivery | mitigate | Post only to `channels.get(siteUrl)`; unmapped -> warn+skip, no default/shared-channel fallback (slackChannelId retired) |
| T-07-11 | Denial of service | duplicate weekly post | mitigate | `claimDailyReport(dateKey)` idempotency lock retained; a claimed key short-circuits the run |
| T-07-12 | Denial of service | one client aborting the run | mitigate | Per-client report + post wrapped so a single failure logs generically and the loop continues |
| T-07-SC | Tampering | npm installs | accept | No new packages — all deps (@upstash/redis, vitest) already installed and version-pinned |
</threat_model>
